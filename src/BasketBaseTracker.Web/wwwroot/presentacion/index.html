El contexto

  • Cada temporada, varios clubes de la provincia de Sevilla organizan competiciones de baloncesto base (benjamín, alevín, infantil, cadete, juvenil...) — los juegos mancomunados.
  • Calendarios, resultados y clasificaciones se llevaban de forma dispersa y manual.
  • Nace como Trabajo de Fin de Máster, con la aspiración de convertirse en una herramienta real para el seguimiento de esta competición.

Simplicidad deliberada: el foco del proyecto estaba en incorporar la IA al flujo de desarrollo, no en construir una arquitectura más compleja y extensible (p. ej. SPA + API separada). Un único proyecto, un único lenguaje, de extremo a extremo.

Decisiones razonadas, no por defecto

  • Clasificación calculada al vuelo, sin tabla materializada — evita una condición de carrera real (lost update) entre administradores editando partidos en paralelo.
  • Caché con TTL, sin purga activa — la consistencia eventual de 5 min que exige el propio documento funcional permite cachear agresivamente sin gestionar un secreto ni una API de purga adicional.
  • Hosting serverless (Container Apps + SQL Serverless, escala a cero) — coherente con una carga muy estacional y presupuesto cero.

Cada decisión documentada con su alternativa descartada en docs/architecture.md

Infraestructura como código con .NET Aspire

  • AppHost.cs declara toda la topología (Web, Azure SQL, Key Vault, Storage...) en C# — un único lenguaje también para la infraestructura.
  • En local, aspire run levanta contenedores equivalentes (SQL Server, Azurite) con un dashboard de logs/trazas/métricas en vivo.
  • En despliegue, aspire deploy genera el Bicep en memoria a partir de ese mismo modelo — no se escribe a disco por defecto; AppHost.cs, ya versionado, es la fuente real de infraestructura como código.

CI/CD: integración, publicación y despliegue

Integración — ci.yml
build + tests en cada push/PR a develop/main, sin secretos de Azure

Publicación — publish.yml
push a main: build + tests + imagen al Azure Container Registry (sin Dockerfile)

Despliegue — deploy.yml
migración de BD + revisión sin tráfico + smoke E2E + promoción

  • Autenticación contra Azure por OIDC (Federated Identity) — sin secretos de cliente en claro
  • Container Apps en modo de revisiones múltiples: la imagen nueva solo recibe tráfico si el smoke E2E pasa contra su propia URL
  • Rollback sin redesplegar: apuntar el tráfico a la revisión anterior

Tecnologías: GitHub Actions (orquestación) · .NET Aspire (modelo de infraestructura) · Azure Container Registry · Azure Container Apps — docs/architecture.md, punto 13

El proceso: desarrollo dirigido por especificaciones

  1. spec.md — qué y por qué, alcance, criterios de aceptación
  2. Aclaraciones — ronda de preguntas antes de planificar
  3. plan.md — cómo, entidades y pantallas afectadas
  4. tasks.md — tareas pequeñas y verificables
  5. Implementación
  6. Cierre — archivado, PR, confirmación humana

Cada incremento (BAS-N) es una conversación estructurada con el asistente de IA, no una única generación de código.

Claude Code multiagente: git worktrees

  • Varias sesiones de Claude Code trabajan en paralelo sobre el mismo repositorio, cada una en su propio git worktree: una copia de trabajo aislada que comparte el mismo historial.
  • Cada worktree vive en su propia rama feature/BAS-N, sin pisarse entre sesiones ni bloquear el checkout principal.

Skills a medida del proyecto

  • El asistente de IA no tiene memoria entre sesiones más allá de lo que está escrito en el repositorio.
  • .claude/skills/aspire y .claude/skills/dotnet documentan las convenciones exactas de las CLIs para este proyecto: cómo scaffoldear el AppHost, gestionar migraciones EF Core, generar CRUD de Razor Pages...
  • Cada bug o comportamiento inesperado de una herramienta, encontrado una vez, se registra en la skill correspondiente — la siguiente sesión no lo vuelve a redescubrir desde cero.

Gobernanza

  • Una rama feature/BAS-N por incremento, creada desde develop
  • main y develop protegidas: sin push directo, PR obligatorio, CI en verde
  • Ningún PR se fusiona sin confirmación humana explícita — ni siquiera con todas las tareas completadas
  • El asistente de IA nunca fusiona ni borra ramas por su cuenta
