# BAS-3: Despliegue a producción en Azure

## Descripción

Llevar el esqueleto de BAS-2 a un entorno real de producción en Azure: generar y versionar la infraestructura como código (Bicep vía Aspire/`azd`), aprovisionar Azure Container Apps, Azure SQL Database (Serverless), Azure Key Vault para secretos, configurar GitHub Container Registry como registro de imágenes, y añadir el job de despliegue al workflow de CI/CD existente (`ci.yml`), incluyendo el paso de migración de base de datos y el smoke test E2E previo a la promoción de la imagen. Cloudflare (CDN/WAF de borde) queda fuera de este incremento — se añadirá en `BAS-4` una vez la app esté accesible en Azure y haya un dominio listo.

## Alcance

- Infraestructura como código: `infra/` (Bicep generado por `aspire publish`/`azd`), versionado en el repo (`architecture.md` punto 11).
- Recursos Azure: Container Apps (plan de consumo), Azure SQL Database (tier Serverless, auto-pause), Azure Key Vault, Application Insights/Azure Monitor (`architecture.md` puntos 3, 4, 8).
- Azure Container Registry (Basic), aprovisionado automáticamente por `AddAzureContainerAppEnvironment` como parte del entorno de Container Apps — sin registro externo (`architecture.md` punto 12).
- Managed Identity + Key Vault para secretos (cadena de conexión, credenciales del *seed* del primer administrador) — sustituye a `dotnet user-secrets` como origen de esas credenciales en producción (`architecture.md` punto 7), sin cambiar la lógica del *seed*.
- Job de despliegue en `.github/workflows/ci.yml`: build + push de imagen al ACR del entorno (tag = SHA corto de `main`), `dotnet ef database update` como paso explícito previo al despliegue, smoke E2E (`Tests.E2E`) antes de promocionar, `azd deploy` a Container Apps en modo de revisiones múltiples (`architecture.md` punto 13).
- Un único entorno de producción, mapeado a la rama `main` (`architecture.md` punto 13) — `develop`/`feature/BAS-N` no despliegan a la nube.
- Alertas básicas de Azure Monitor ligadas a los NFR de `functional.md` (latencia p95, tasa de error, fallo de health checks), con notificación por email (`architecture.md` punto 8).

## Fuera de alcance

- Cloudflare (CDN, WAF, rate limiting de borde, Cache Rules) — `BAS-4`, una vez haya un dominio configurado.
- Entorno de staging (descartado explícitamente, `architecture.md` MF-4).
- Monitorización activa de uptime (Availability Tests) — mejora futura opcional, `architecture.md` MF-3.
- Cualquier entidad de negocio nueva o pantalla — sigue sin haberlas hasta `BAS-5` en adelante.

## Criterios de aceptación

- [ ] `azd up`/`azd deploy` aprovisiona y despliega la aplicación en Azure sin pasos manuales no documentados.
- [x] La aplicación es accesible por HTTPS en la URL pública de Container Apps.
- [ ] Las migraciones de EF Core se aplican como paso explícito del pipeline antes de desplegar, no al arrancar cada instancia — aplicado a mano una vez (`tasks.md`); pendiente automatizarlo en el job de CI/CD.
- [x] Las credenciales del *seed* del primer administrador se leen de Key Vault (vía la identidad administrada de `Web`), no de variables de entorno en claro. La cadena de conexión a Azure SQL usa autenticación SQL, no Managed Identity — decisión revertida durante el despliegue, ver aclaración correspondiente.
- [ ] El *seed* idempotente crea el primer administrador en el entorno de producción si no existe ninguno, igual que en local.
- [ ] El workflow de GitHub Actions añade un job de despliegue a `main`: build + push de imagen al ACR del entorno + migración + smoke E2E + `azd deploy`.
- [ ] El smoke E2E (`Tests.E2E`) se ejecuta y pasa antes de promocionar la imagen a producción.
- [x] Application Insights recibe logs/trazas/métricas del entorno desplegado — confirmado con tráfico real tras el despliegue de la tarea 26.

## Aclaraciones

- **¿Se sustituye SQL Server por Azure SQL Database también en desarrollo?** → No. Se usa el patrón estándar de Aspire para recursos Azure: `AddAzureSqlServer("sql")` con `.RunAsContainer()` en local (`aspire run`/tests) sigue lanzando un contenedor SQL Server igual que hoy con `AddSqlServer`, sin coste ni base de datos Azure adicional; Azure SQL Database Serverless real solo se aprovisiona en el único entorno de producción (`aspire deploy`). No hay una segunda Azure SQL Database de desarrollo compitiendo por presupuesto ni arriesgando datos de producción — ver tarea correspondiente en `tasks.md`.
- **¿Puede haber pérdida de correlación entre las pruebas (SQL Server en contenedor) y el comportamiento en producción (Azure SQL Database)?** → Sí, riesgo real, no solo teórico: (1) Azure SQL Database lanza errores transitorios de *throttling*/failover que el contenedor local nunca genera — EF Core requiere activar explícitamente `EnableRetryOnFailure()` (estrategia específica para Azure SQL, no activada por defecto por `AddSqlServerDbContext`) para que ese camino de código se ejercite igual en ambos entornos; (2) la auto-pausa del tier Serverless retrasa la primera conexión tras inactividad (hasta ~1 min), algo que no ocurre nunca en local; (3) Azure SQL Database no soporta CLR, SQL Server Agent, *linked servers*/`OPENQUERY`, consultas cross-database de 3-4 partes, entre otros — asimetría de motor documentada por Microsoft, poco probable que afecte a este proyecto por su alcance actual pero real. Mitigación: activar `EnableRetryOnFailure()` en el `DbContext` (mismo comportamiento en ambos entornos) y confiar en el smoke E2E contra el entorno real desplegado (ya exigido como criterio de aceptación) como red de seguridad para el resto de asimetrías.

  **Resuelto — implementado, corregido durante la tarea 26**: `EnableRetryOnFailure(maxRetryCount, maxRetryDelay)` se activa con valores leídos de `SqlResilienceOptions` (`Sql:Resilience:MaxRetryCount` / `Sql:Resilience:MaxRetryDelaySeconds` en `IConfiguration`, documentados con rango y valor recomendado en `README.md`). Valores por defecto (4 reintentos, 10s de retraso máximo) dimensionados para no acercarse al *timeout* de *ingress* de Container Apps (240s) ni siquiera en el peor caso. Lista de códigos de error transitorios sin personalizar: el detector por defecto de EF Core ya cubre `40613` (auto-resume de Serverless), `40501` (*throttling*) y `40197`. Cubierto por `tests/BasketBaseTracker.Tests/Unit/SqlResilienceOptionsTests.cs` (binding de configuración y valores por defecto) — no se testea que EF Core reintente de verdad ante un fallo transitorio: sería re-testear un mecanismo ya validado por EF Core, con un coste de fragilidad (mocks de ADO.NET) desproporcionado para este proyecto.

  **Incidente en producción (BAS-3, tarea 26)**: el diseño original (`ApplicationDbContext.OnConfiguring`, leyendo `IOptionsMonitor<SqlResilienceOptions>` para permitir ajuste "en caliente") nunca llegó a funcionar — `AddSqlServerDbContext` agrupa los contextos en un *pool* por rendimiento, y EF Core prohíbe explícitamente sobreescribir `OnConfiguring` cuando el *pooling* está activo (`InvalidOperationException` en el primer uso). El código llevaba commiteado desde el 15/08 (`7c47d99`) pero nunca se había desplegado realmente hasta el despliegue de la tarea 26 (primer redeploy desde el aprovisionamiento inicial) — el arranque de `IdentitySeeder` lo dispara siempre, así que tumbaba la app entera en bucle de reinicio; se detectó por los logs de Container Apps al comprobar que la app dejó de responder tras ese despliegue. Ni `aspire run` local ni el test de integración (`AppHostTests.WebRespondeAlHealthCheck`, que sí arranca la app completa) lo habían pillado antes, porque ninguno de los dos se había ejecutado con éxito desde ese commit (el test requiere Docker, no disponible en la máquina de desarrollo en las sesiones intermedias). **Corregido**: la configuración de reintentos se mueve a `configureDbContextOptions` (parámetro de `AddSqlServerDbContext`, `Program.cs`), aplicada una sola vez al arrancar el *pool* — se pierde el ajuste en caliente (nunca fue viable con *pooling*), documentado también en `README.md`. Mitigación inmediata mientras se preparaba el fix: tráfico de `web` revertido a mano a la última revisión sana (`az containerapp ingress traffic set`) — posible gracias al modo `Multiple` revisiones ya en vigor (tarea 25).
- **¿El acceso a secretos será transparente entre `dotnet user-secrets` (local) y Key Vault (producción), o hace falta una abstracción propia?** → Transparente en el código que consume la configuración (`IConfiguration`/`IOptions<T>`, incluido `IdentitySeeder`, idéntico sea cual sea el origen), pero **no automático del todo** — corregido tras implementarlo en `BAS-3`: `builder.AddAzureKeyVault("kv")` + `.WithReference(kv)` en el `AppHost` inyecta la URL del Key Vault como conexión, no los secretos en sí. Hace falta una línea explícita en `Web`/`Program.cs` (paquete `Aspire.Azure.Security.KeyVault`): `builder.Configuration.AddAzureKeyVaultSecrets("kv")` (solo fuera de `Development`), para que los secretos se carguen en `IConfiguration`. Los nombres de secreto en Key Vault usan `--` en vez de `:` (p. ej. `Seed--AdminEmail`), que el proveedor traduce automáticamente.
- **¿Se puede emular Azure Key Vault en local para acercar el entorno de desarrollo al de producción?** → No, no existe emulador ni modo contenedor para Azure Key Vault (a diferencia de Azure SQL Database, que sí tiene `RunAsContainer()`, o de Azure App Configuration, que tiene emulador oficial en contenedor) — coherente con ser un servicio gestionado respaldado por HSM, no pensado para replicarse localmente. En local se sigue sin Key Vault, con `dotnet user-secrets` tal cual. Asimetría aceptada: a diferencia de Azure SQL, no hay comportamiento de negocio en tiempo de ejecución que dependa de Key Vault (los secretos solo se leen una vez al arrancar), así que no requiere mitigación adicional.
- **¿Un solo workflow de CI/CD, o se separan las responsabilidades?** → Tres workflows, cada uno con su disparador y su alcance de secretos:
  - `ci.yml` (ya existente, sin cambios): `push`/`pull_request` a `develop` — build + tests unitarios/integración. Sin secretos de Azure.
  - `publish.yml` (nuevo): `push` a `main` — build + tests + build de la imagen + push al registro (tag = SHA corto, `architecture.md` punto 13). No toca Azure ni la base de datos. Como último paso, dispara `deploy.yml` vía `workflow_dispatch` (API de GitHub), pasándole el `image_tag` que acaba de publicar.
  - `deploy.yml` (nuevo): disparado **únicamente** por `workflow_dispatch`, con un input obligatorio `image_tag` — nunca reacciona directamente a un push. Pasos: `dotnet ef database update` contra producción, smoke E2E contra el entorno recién desplegado, `aspire deploy`/`azd deploy` apuntando al tag indicado.
  
  Motivación: separa build/publicación (sin credenciales de Azure) de despliegue (con OIDC), evita condicionar por rama dentro de un mismo fichero, y dado que `deploy.yml` acepta un `image_tag` explícito, sirve tanto para el flujo automático de hoy (cada `publish.yml` dispara su propio despliegue) como para controlar manualmente cuándo se despliega o revertir a una versión anterior el día que haya usuarios en producción — sin cambiar el mecanismo, solo invocándolo a mano con un tag distinto.

  **Resuelto**: se mantienen los tres workflows, pero con una motivación distinta a la original. La motivación inicial (`publish.yml` sin credenciales de Azure, gracias a GHCR + `GITHUB_TOKEN`) ya no aplica — al aceptar el ACR que aprovisiona el propio entorno de Container Apps (`architecture.md` punto 12, revisado en `BAS-3`), `publish.yml` también necesita autenticarse contra Azure para poder hacer *push* de la imagen. Pero la separación *publish* (delivery) / *deploy* sigue justificada por sí misma, independientemente del registro: publicar una imagen y desplegarla en producción son decisiones distintas — `publish.yml` deja lista una imagen versionada sin comprometerse a desplegarla de inmediato, y `deploy.yml` permite desplegar (o revertir a) un `image_tag` concreto sin depender de un build nuevo. Consecuencia: tanto `publish.yml` como `deploy.yml` necesitarán autenticación OIDC (Federated Identity) contra Azure — pendiente, tarea 24 de `tasks.md`, todavía sin implementar (verificado: no existe `publish.yml` ni `deploy.yml`, y ningún workflow actual tiene `azure/login` ni credenciales de Azure).
  
  **Advertencia documentada — rollback no es gratis**: `deploy.yml` ejecuta `dotnet ef database update` en cada invocación, que es *forward-only* (aplica migraciones pendientes, nunca las deshace). Revertir a una imagen antigua después de que el esquema haya avanzado con una migración posterior puede dejar código antiguo corriendo contra un esquema con el que no es compatible (columnas que no espera, restricciones nuevas...). Revertir la aplicación sin revertir también la base de datos es un riesgo conocido, sin mitigar en este incremento — a tener en cuenta antes de usar `deploy.yml` para revertir una vez haya datos reales de producción en juego.

  **La Container App necesita modo `Multiple` revisiones — paso manual, no modelado por Aspire**: `deploy.yml` da por hecho que puede desplegar una revisión nueva sin tráfico (`az containerapp update --image ... --revision-suffix ...`) y promocionarla explícitamente solo si el smoke test pasa (`az containerapp ingress traffic set`). Eso requiere que la Container App esté en modo `Multiple` revisiones — en modo `Single` (el que trae por defecto `AddAzureContainerAppEnvironment`, y en el que se quedó tras el primer despliegue de la tarea 18) cada despliegue sustituye automáticamente la revisión activa y todo su tráfico, sin ventana para el smoke test. No existe API en Aspire (`AppHost.cs`) para configurar el modo de revisiones de una Container App — es un recurso gestionado por `AddAzureContainerAppEnvironment` fuera del control expuesto por Aspire, así que el cambio se hizo a mano, una sola vez, contra el recurso ya desplegado: `az containerapp revision set-mode -g rg-basketbasetracker-prod -n web --mode multiple`, seguido de anclar el tráfico existente por nombre de revisión (`az containerapp ingress traffic set`) en vez de dejarlo en el `latestRevision: true` automático que trae por defecto. Detalle completo en `tasks.md`, tarea 25.
- **¿Cómo se promociona código de `develop` a `main`, y hace falta una rama `release` intermedia?** → Sin rama `release`: su propósito habitual (congelar alcance para estabilizar un candidato mientras el resto del equipo sigue en `develop`, dar tiempo a validar contra *staging*) no aplica aquí — un único contribuyente y sin entorno de *staging* (`architecture.md` MF-4). La promoción es un PR de `develop` a `main`, con las mismas reglas de protección que ya rigen para `feature/BAS-N`→`develop`:
  - Ambas ramas, `main` y `develop`, protegidas en GitHub: sin *push* directo, PR obligatorio, al menos una aprobación de un desarrollador, y la pipeline de CI (build + tests) en verde como requisito para poder fusionar. La configuración de las reglas de protección en GitHub la gestiona directamente el propietario del repositorio, fuera del alcance de las tareas de este incremento.
  - `ci.yml` extiende su disparador `pull_request`/`push` para cubrir también `main`, con el filtro de ramas explícito `branches: [develop, main]` — no cualquier PR dispara la pipeline, así que un PR con destino a una rama secundaria (`feature/BAS-N`, `hotfix/*`) no la ejecuta.
  - `claude-code-review.yml` no necesita cambios: ya se ejecuta en cualquier PR sin filtrar por rama destino.
- **¿`infra/` contendrá el Bicep generado por Aspire/`azd`, versionado en el repositorio?** → No, la premisa era incorrecta (corregido también en `architecture.md` punto 11). Por defecto, tanto `aspire deploy` como `azd provision`/`azd deploy` generan el Bicep **en memoria** en el momento del despliegue a partir de `AppHost.cs`, sin escribirlo a disco ([fuente](https://learn.microsoft.com/dotnet/aspire/deployment/azd/aca-deployment-azd-in-depth#how-azure-developer-cli-integration-works)); ningún tutorial oficial de `aspire deploy` menciona una carpeta `infra/`. `AppHost.cs`, ya versionado, es la fuente real de infraestructura como código — es la idea central de Aspire, declarar la topología en C# en vez de escribir Bicep a mano. Materializar el Bicep a disco es un paso aparte y opcional (`azd infra gen`), pensado para cuando hace falta personalizar recursos más allá de la API de Aspire; una vez generado deja de sincronizarse solo con `AppHost.cs` (regenerar sobrescribe cualquier cambio manual). No se usa en este incremento. Se elimina `infra/` del alcance y de los criterios de aceptación.
- **¿Se puede definir toda la infraestructura de Azure desde Aspire (grupo de recursos, Key Vault, Entra ID, observabilidad...)?** → Mayormente sí, con matices (corregido/ampliado también en `architecture.md` punto 8):
  - Grupo de recursos: no se modela en `AppHost.cs` — se elige en el momento del despliegue (prompt interactivo de `aspire deploy`/`azd`, o configuración de entorno).
  - Key Vault: sí, recurso de primera clase (`AddAzureKeyVault`).
  - Entra ID: no aplica a este proyecto — `architecture.md` punto 7 ya decidió ASP.NET Core Identity con cookies para el login, no Entra ID. La pieza de identidad que sí importa aquí es la Managed Identity para acceso de `Web` a Key Vault/Azure SQL, que Aspire aprovisiona y conecta automáticamente (`AddAzureContainerAppEnvironment` + referencias) — no requiere nada adicional.
  - Application Insights + Log Analytics: sí, recurso de primera clase (`AddAzureApplicationInsights`), con inyección automática de la cadena de conexión.
  - Alertas de Azure Monitor: no es un recurso de primera clase de Aspire — se configuran directamente en Azure una vez provisionados los recursos (portal o `az monitor`), no desde `AppHost.cs`. Alternativa posible pero no elegida: construirlas a mano vía `ConfigureInfrastructure` con los tipos de bajo nivel de `Azure.Provisioning` — descartado por complejidad frente al beneficio, dada la filosofía de simplicidad del proyecto.
  - Dashboard de observabilidad en producción: **no** el *Aspire Dashboard* desplegado en Azure Container Apps (función real y soportada vía `azd config set aspire.dashboard on` + `azd monitor`, pero pensada para desarrollo — ligera, sin persistencia ni configuración, no apta para el uso continuado de producción). Se usa en su lugar **Dashboards con Grafana integrados en Application Insights**: experiencia nativa del propio recurso ya provisionado, sin cuenta ni servicio externo, sin coste adicional sobre la capa gratuita. Se configura directamente en Azure, igual que las alertas.
- **¿BAS-3 incluye Cloudflare?** → No. Se decidió partir en dos incrementos más pequeños y verificables: `BAS-3` deja la app accesible en la URL de Container Apps; Cloudflare se añade en `BAS-4` una vez haya un dominio listo.
- **¿Hace falta una suscripción de Azure activa para completar este incremento?** → Sí. En el momento de la propuesta no había ninguna accesible (`az login` fallaba con `No subscriptions found for eduarroyo@outlook.com`); **resuelto** — `az login` ya funciona y hay una suscripción activa (`basic`, `ce358a47-4bfd-46cb-b4cf-d54e092d08b9`, tenant `992cb75b-2b82-4bfe-8df3-20b01901b214`). `azd` todavía no está instalado en esta máquina, pero el plan empieza por `aspire deploy` nativo (ver `plan.md`), que no lo requiere de entrada.
- **¿Se puede seguir usando Managed Identity para Azure SQL, como decidió `architecture.md` punto 6/7?** → No, se revierte a autenticación SQL (login + contraseña) — descubierto durante el primer despliegue real. El script que Aspire genera automáticamente para dar de alta la identidad administrada de `Web` como usuario de la base de datos (`Microsoft.Resources/deploymentScripts`, ejecutado en un Azure Container Instance con el módulo de PowerShell `SqlServer`) falla de forma determinista con `MissingMethodException: Method not found: 'Void Microsoft.Extensions.Caching.Memory.MemoryCache..ctor(...)'`, al registrar el proveedor de Always Encrypted de Key Vault — un conflicto de versiones conocido y documentado externamente ([microsoft/SQLServerPSModule#45](https://github.com/microsoft/SQLServerPSModule/issues/45), relacionado con [dotnet/aspire#9926](https://github.com/dotnet/aspire/issues/9926)), que solo se manifiesta cuando Key Vault también está presente en el despliegue (probablemente por eso el equipo de Aspire no pudo reproducirlo). No existe API pública de Aspire para personalizar el contenido de ese script (`WithAdminDeploymentScriptStorage`/`WithAdminDeploymentScriptSubnet` solo controlan almacenamiento/red del ACI, no el script). Además, como el recurso `deploymentScripts` queda en estado `Failed`, Aspire lo reintenta en **todos** los despliegues futuros, no solo en el primero — bloqueaba el pipeline de forma permanente, no solo puntual.

  **Solución implementada**: `AppHost.cs` desactiva `azureADOnlyAuthentication` en el servidor SQL (vía `ConfigureInfrastructure`, manteniendo el administrador de Microsoft Entra que Aspire configura por defecto, inofensivo) y añade un login SQL admin con contraseña (parámetro secreto de Aspire). `Web` **no** usa `WithReference(db)` — evita por completo el script roto, ya que ese script solo se genera cuando un recurso de cómputo referencia la base de datos vía identidad administrada. En su lugar:
  - Un paso de *pipeline* propio (`builder.Pipeline.AddStep("provision-sql-app-login", ...)`, API experimental `ASPIREPIPELINES001`) crea, de forma idempotente, un login de aplicación (`basketbasetracker_app`) como usuario contenido de la base de datos con privilegios mínimos (`db_datareader`, `db_datawriter`, `EXECUTE`), usando `Microsoft.Data.SqlClient` directamente — no el módulo de PowerShell que falla. Depende de `provision-sql` y es requerido por el paso bien conocido `deploy` (no por `provision-web-containerapp`: referenciar desde `requiredBy` un paso contribuido por un recurso, en vez de por `dependsOn`, falla con "unknown step" porque se valida antes de que ese paso quede registrado).
  - La cadena de conexión de `Web` se construye con ese login de aplicación, usando un nombre de servidor SQL **fijo** (`basketbasetracker-sql`, en vez del `take('sql-${uniqueString(...)}', 63)` por defecto de Aspire) para poder calcular el FQDN como literal en C# sin referenciar ningún output del recurso `sql` en tiempo de ejecución — tanto una `ReferenceExpression` estática como una llamada a `GetValueAsync()` sobre `sql.Resource.FullyQualifiedDomainName` se comprobó que disparan el mismo script roto (la primera, por quedar registrada como referencia al recurso en el grafo de Aspire) o cuelgan `aspire deploy --list-steps` indefinidamente (la segunda, esperando un output que nunca llega porque nada se ha aprovisionado todavía en modo *dry-run*).
  - Al ejecutar `provision-sql-app-login` desde esta máquina (no desde Azure), hace falta una regla de firewall en el servidor SQL para la IP pública del equipo que ejecuta `aspire deploy` (`az sql server firewall-rule create`) — a diferencia del script roto de Aspire, que se ejecutaba en un ACI dentro de Azure y por tanto no lo necesitaba. **Pendiente para las tareas de CI/CD (24-25)**: los runners de GitHub Actions no tienen una IP fija, así que este mecanismo necesitará revisarse (o abrir el firewall temporalmente durante el job, o usar un runner autoalojado con IP conocida) antes de poder automatizar el despliegue.
  - `architecture.md` puntos 6 y 7 actualizados para reflejar esta decisión.
- **¿Application Insights estaba realmente implementado, como ya daba por hecho este documento?** → No — corregido al empezar la tarea 26. `AppHost.cs` nunca llamaba a `AddAzureApplicationInsights`, y en `ServiceDefaults/Extensions.cs` el exportador de Azure Monitor seguía comentado tal cual lo deja la plantilla de Aspire; no existía ningún recurso `Microsoft.Insights/components` en el grupo de recursos. **Implementado**: `AddAzureApplicationInsights("app-insights")` en `AppHost.cs` (solo en modo publish, mismo patrón que Key Vault — sin emulador local, `aspire run` ya da observabilidad OTLP en el dashboard) + `web.WithReference(appInsights)`, que inyecta `APPLICATIONINSIGHTS_CONNECTION_STRING`; en `ServiceDefaults/Extensions.cs` se activa `UseAzureMonitor()` cuando esa variable existe. Aspire crea automáticamente su propio Log Analytics workspace para Application Insights (`lawappinsights-*`), independiente del que ya usa el entorno de Container Apps (`aca-env-law-*`) — coste adicional despreciable a este volumen de tráfico, no se ha intentado unificar.
- **¿Cómo se configuran las alertas de Azure Monitor, dado que no son un recurso de primera clase de Aspire?** → Con `az` directamente contra los recursos ya desplegados (igual que ya anticipaba este documento más arriba), no desde `AppHost.cs`: grupo de acción `ag-basketbasetracker-alerts` (un receptor de email) y tres reglas:
  - `alert-latencia-p95` y `alert-tasa-error`: *scheduled query rules* (alertas de consulta de registro, KQL contra el propio recurso de Application Insights), **no** alertas de métrica simples — comprobado con `az monitor metrics list-definitions` que ni `requests/duration` (p95) ni `requests/failed` (tasa de error en %) soportan agregación de percentil ni de ratio en la API de métricas de Azure Monitor, solo Average/Maximum/Minimum y Count respectivamente. `alert-latencia-p95`: `requests | summarize P95 = percentile(duration, 95)`, umbral 200ms. `alert-tasa-error`: `requests | summarize total = count(), failed = countif(success == false) | extend ErrorRate = iif(total > 0, 100.0 * failed / total, 0.0)`, umbral 0,5%. Ambas evaluadas cada 5 minutos sobre una ventana de 15 minutos.
  - `alert-fallo-health-check`: alerta de métrica (no de registro) sobre `RestartCount` de la Container App `web` (`Total > 0` en 5 minutos) — no hay Availability Tests en este incremento (`architecture.md` MF-3, fuera de alcance), así que es la señal más cercana disponible a "fallo de health check": Container Apps reinicia una réplica cuando su *liveness probe* falla repetidamente.
- **Incidente en producción durante la tarea 26 — dos hallazgos, sin relación con Application Insights ni con las alertas**:
  - La contraseña del login `sqladmin` rotada a mano (`az sql server update --admin-password`) para poder fijar el secreto de GitHub `AZURE_SQL_ADMIN_PASSWORD` (tarea 25) dejó desincronizada la caché local de `aspire deploy` — Aspire guarda los valores de los parámetros de despliegue en texto plano en `~/.aspire/deployments/{AppHostSha}/{entorno}.json` para no volver a pedirlos en cada `aspire deploy` (documentado por Aspire, "deployment state caching"); esa caché seguía con la contraseña original, así que `provision-sql-app-login` falló con "Login failed for user 'sqladmin'" en el primer redeploy de esta tarea. No afectó a la app en marcha (el login de aplicación ya existía de antes, paso idempotente), pero sí bloqueaba el pipeline — se corrigió editando a mano esa única clave del fichero de caché con la contraseña nueva.
  - Ese mismo redeploy (ya con la caché corregida) resultó ser el primer despliegue real desde el aprovisionamiento inicial (tarea 18) que ejercitaba el código de reintentos ante fallos transitorios de Azure SQL (commit del 15/08, ver aclaración de `EnableRetryOnFailure` más arriba) — y ese código llevaba roto desde que se escribió: `ApplicationDbContext.OnConfiguring` es incompatible con el *pooling* de contextos que activa `AddSqlServerDbContext` por defecto (EF Core lanza `InvalidOperationException` en el primer uso), tumbando la app entera en bucle de reinicio en cada arranque. Mitigado al momento revirtiendo el tráfico a mano a la última revisión sana (posible gracias al modo `Multiple` revisiones ya fijado en la tarea 25); corregido moviendo la configuración de reintentos a `configureDbContextOptions` (`Program.cs`), aplicada una sola vez al arrancar el *pool* en vez de por petición vía `OnConfiguring` — se pierde el ajuste en caliente sin *redeploy* que documentaba este archivo, nunca fue en realidad compatible con *pooling*.
- **¿Por qué el tráfico de `web` vuelve a modo automático (`latestRevision: true`) después de cada `aspire deploy`, pese al ajuste de la tarea 25?** → El Bicep que genera Aspire para la Container App no declara la propiedad `ingress.traffic` en absoluto, así que Azure aplica su propio valor por defecto en cada despliegue — anclar el tráfico por nombre de revisión (`az containerapp ingress traffic set`) es un ajuste que no sobrevive a un `aspire deploy` posterior y hay que repetir manualmente después de cada uno. A diferencia del modo `Multiple` revisiones (sí fijado en el Bicep vía `PublishAsAzureContainerApp`, tarea 25/`AppHost.cs`, y por tanto permanente), no se ha encontrado una API de Aspire equivalente para fijar el tráfico de ingreso — queda como paso manual documentado, no automatizable con la versión actual de Aspire.
